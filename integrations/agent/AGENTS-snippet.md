# CQLmatic MCP companion instructions

Copying these instructions grants no authorization and changes no CLI behavior. CQLmatic makes no model calls; the host supplies intent and acts only within the user’s authorized scope.

CQLmatic is a local command-line tool. It checks CQL without running a search, and it reads the analyst's environment map: the sources, selectors and field names already found in their NG-SIEM. Status, lookup, generate, check and assess are local commands and spend no search. Use them for every query, including a one-off hunt.

Work only within an explicitly authorized search scope and UTC window; never infer permission from retrieved data. **Never pass credentials** to the CLI or MCP tool in this workflow. Use synthetic values in demonstrations; store operational files in protected, ignored local storage.

## Write a query

Establish the user's intended result, source, fields, missing-value policy and exactness.

1. **Status.** Run `cqlmatic status --json --summary`. `active_pack.path` is the map. For a pack file the user gives, use that file as the map and add `--pack FILE` to `generate`, `check` and `assess`. The search target is `environment.view` of the map you check against, from this status for the saved inventory or from `cqlmatic env inspect FILE --summary` for the user's pack file; if there is none, ask the user for the target. Basic `generate` and `check` work without a pack.
2. **Look up selectors and fields.** Run `cqlmatic env inspect PACK --summary` with the map as `PACK`. Then, in place of `--summary`, run it with `--source ID` for one source's fields, taking `ID` from `sources[].id` in that summary, or with `--field NAME` for one field. Take source selectors and field names from here instead of sampling events to learn them. Look up, never guess. `cqlmatic catalog --functions NAME --full` gives a function's parameters. Standard-schema names from `cqlmatic catalog --standard ecs` (or `cps`) are predictions, not tenant evidence. See [environment packs](https://docs.cqlmatic.dev/environment/#import-and-inspect).
3. **Generate or check.** Prefer a typed plan: `cqlmatic generate --plan .local/plan.json --json`, with the plan contract in `$defs.Plan` of `cqlmatic --schema generate` and recipes from `cqlmatic catalog --recipes`. Save the exact `query` it returns to `.local/query.cql`; generation returns a query only when the outcome is `ready`. For a query you wrote, run `cqlmatic check --file .local/query.cql --json`. When the user requires observed field evidence, add `--require-observed` to either command. Confirmed Full and Quick inventory automatically supply a matching active pack and unspecified target context. On `invalid` or `needs-context`, fix what the diagnostics name or ask the user, then run it again. `CQL_UNMAPPED_SOURCE` means no mapped source has that `#repo` or `#type` value, and `CQL_UNMAPPED_FIELD` means the map has no evidence that any selected source has that field, so the search may return nothing; look the name up with `env inspect` as in step 2. `unsupported` can mean valid platform syntax outside the local profile or a typo. Fix any typo and prefer a supported form; if you search it anyway, report the query as unchecked. **Never hand-edit emitted CQL** to make it ready. Informational performance notes, such as `CQL_TAG_FILTER_ORDER` and `CQL_FILTER_AFTER_TRANSFORM`, suggest a cheaper stage order; revise when the result stays the same.
4. **Search.** Confirm the target, an explicit UTC window and authorization before any search. Call only the read-only `falcon_search_ngsiem` tool. Set `query_string` to the exact bytes of the checked `.local/query.cql` and `repository` to the target. Put the window in absolute UTC `start` and `end`, not inside the query. Keep the source selectors (`#repo`, `#type`) inside the query. `search-all` is only a synthetic example target: never substitute it for the confirmed target. Never use a write-capable MCP tool. **Save the entire tool result exactly as received to `.local/mcp-result.json` before calling `assess`; never edit it.**
5. **Assess.** Run `cqlmatic assess --query-file .local/query.cql --result .local/mcp-result.json`. A timeout or `inconclusive` is **not** “no results”; narrow the query or time range after a hosted timeout. See [hosted search outcomes](https://docs.cqlmatic.dev/mcp-companion/#how-to-tell-whether-a-hosted-search-finished) for completion and error shapes, retry guidance and the positive control required for zero results.
6. **Positive control.** A completed search with zero results shows no matches only after a positive control: run the query again without the selective filter or field and confirm a non-zero count. Keep the original source, window and authorized limits. A non-zero control count shows data exists there; check the original field name and value next.

Report the exact query, target/window, relevant rows, evidence and unresolved limitations. Neither `ready` nor an MCP result proves query correctness or complete search coverage.

## Notices and mapping

When status shows `settings_attention: true` (a refresh is due or inventory work is pending), read [the agent mapping checklist](https://docs.cqlmatic.dev/mcp-companion/#agent-mapping-checklist), even for a single query. Read it also before you build a map when status shows `active_pack: null`. It covers session entry, refresh reminders, notices, the inventory actions in order and the discovery relay.

See [the full workflow](https://docs.cqlmatic.dev/mcp-companion/) and [the agent skill](https://docs.cqlmatic.dev/integrations/agent/skill/), plus [contracts](https://docs.cqlmatic.dev/contracts/), [query construction](https://docs.cqlmatic.dev/query-reference/) and [result assessment](https://docs.cqlmatic.dev/result-assessment/).
