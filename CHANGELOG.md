# Changelog

## Unreleased

- Mapping through an agent is easier to follow. Brief inventory output adds a `next_action` while probes are ready, naming the `discovery-step` call that lists their arguments; 0.1.9 gave only a count. `prepare-discovery` with an unknown `source_ids` entry now says that IDs are the `id` values of expected sources in status and that omitting the field selects every expected source. An inventory request that lacks a required field is refused with that field's name. The agent skill lists the inventory actions for building the map in order, through `reconcile`, ahead of the standalone discovery loop.

## 0.1.9

- Later releases can inspect checkpoints written by 0.1.8. For example, a paused run with a retained `completed-unusable` answer keeps that history if measurement rules change, provided the retained bytes still decode as a complete list. The 0.1.8 reader omitted its own version from the lists of producers admitted after a version bump.
- Inventory can continue past a retained 0.1.6 or 0.1.7 MCP discovery run after its original active-time allowance expires and the checkpoint proves it retained one distinct final answer from the hosted search tool. For example, `prepare-scout` can record a qualifying run as `failed` while preserving its checkpoint for inspection. 0.1.8 continued to block on those runs.
- Refresh and capability settlement explain how to use `lifetime-expired` after a recognized poll failure from the hosted search tool. For example, with a 60-second retained lifetime and a reply at 12:00:10 UTC, use that arrival time for `search_started_at` and settle at or after 12:01:10 UTC. For capability, retain the reply as `result_file`; the case stays `unknown`. The 0.1.8 guidance omitted the time from which to count the wait.
- Discovery responses report mapping cost in searches. `relay.cost` in `prepare-discovery`, `dispatch-discovery`, `discovery-step` and `env discover --mcp` output holds `searches.used`, `searches.ready`, `searches.limit` and `answer_bytes`, with `searches.expected_low` and `searches.expected_high` where the range can be stated before the first answers; the offline plan from `env discover --request FILE` reports the same range under `searches`. Quick sources + fields needs 13 to 30 searches per source. The inventory guide adds a reference measurement of what a relayed search cost an assistant, by model.
- `check` and `generate` add informational performance notes for stage order and costly stages: `CQL_TAG_FILTER_ORDER` (`ComputerName=a | #event_simpleName=ProcessRollup2`), `CQL_FILTER_AFTER_TRANSFORM` (`y := lower(a) | ComputerName=b`), `CQL_SORT_COST` and `CQL_SPLIT_COST` (`sort` or `split` with no earlier filter), `CQL_WILDCARD_IGNORE_CASE` and `CQL_REGEX_ALL_FIELDS` (`#repo=x | /powershell/i`). They keep `ready` and do not affect `--fail-on-warning`. 0.1.8 reported none of these.
- `CQL_GROUNDING_LENIENT` is one warning per result instead of one per field. It names the fields that lack qualifying deployment evidence, comes after the diagnostics about the query itself, and leaves the evidence for each field in `grounding.basis`. 0.1.8 emitted a separate warning for every such field.
- `join`, `selfJoin` and `selfJoinFilter` inside a function argument report `CQL_JOIN_PLACEMENT`, as in `groupBy(k, function={join({y=1}, field=k) | count()})` and `stats(selfJoin(k, where=[{a=1},{b=2}]))`. 0.1.8 accepted them. These functions belong at the top level of the query or of a `join` subquery. `selfJoin` combined with `defineTable` reports `CQL_TABLE_JOIN_CONFLICT`, as `join` and `selfJoinFilter` already did.
- Scrappy mode: `cqlmatic env capture --client CLIENT --server NAME` reads the payload an agent's client passes to a hook after a tool call, and records the agent's finished searches in the confirmed inventory without sending results back through the model. A plain event search that names one confirmed expected source becomes a captured observation, a category of its own listed in status as `captured_observations` and labelled `client-hook-capture`, with private copies of its query and result kept beside the state. Captured observations ground `--require-observed` checks with the basis `captured search observation` and the warning `CQL_CAPTURED_OBSERVATION`, and do not change the reconciliation fingerprint. A search that returns rows from another source queues that source as pending inventory work. A captured search may span more than seven days. Captures replace one another: an earlier capture is dropped once later-starting captures of the same source show every field it showed, and copies that no saved observation's audit record names are removed after ten minutes. Each state file keeps its copies and `tally.json` in its own `<state file>.captures` folder. Other searches are counted by outcome in `state.json.captures/tally.json`. The command prints nothing and always exits 0. `--client` selects the payload format: `claude-code`, `cline`, `codex`, `copilot-cli`, `copilot-app`, `copilot-vscode`, `cursor`, `gemini-cli`, `kiro`, `qwen-code`, or `generic` for any other client, plugin or wrapper script that supplies the tool name, arguments and result. The OpenCode plugin `examples/capture/opencode-plugin.js` uses the generic form. For a client whose hook cannot pass a result, `cqlmatic env pass-through -- COMMAND` runs the MCP server command, passes its messages through unchanged and records finished searches the same way. The agent skill gains a short note on both. `import-query-observations` accepts the new label; inventory and status schemas list it.
- `cqlmatic skill install --client CLIENT` writes the agent skill into the selected client's user-level skill directory: `claude-code` uses `~/.claude/skills`, and `codex`, `vs-code` and the Copilot surfaces use `~/.agents/skills`; `CLAUDE_CONFIG_DIR` and `COPILOT_HOME` relocate their clients. `--dir DIR` targets another host. The installed `cqlmatic-companion` folder holds `SKILL.md` and every guide it links to, so the skill reads the same without the source tree. A verified setup names the command for its client in `next_actions`. In 0.1.8 the skill shipped only as a source file with links that resolved inside the repository.
- On Windows, protection checks for existing private directories and files are made through direct system calls. 0.1.8 started PowerShell for each check, so inventory and discovery commands that verify many paths run faster. The owner, access-rule and ancestor conditions and the `SETUP_PROTECTION` diagnostics are unchanged. Creating a private directory still uses the fixed PowerShell helper.

## 0.1.8

- Repeated discovery answers are refused as reused only when they carry a non-empty `trace_id` or a recognized cutoff job identifier. Identical identifier-free answers can end separate attempts after explicit resume.

- Free text after an aggregate reports `CQL_FREE_TEXT_AFTER_AGGREGATE`, including quoted strings, standalone regexes and fieldless `wildcard()` at nested depths. For example, `groupBy(y) | head 10` and `count() | "*"` were accepted in 0.1.7; use `head(10)` or bare match-all `*`. Field comparisons remain valid; `join` and `defineTable` subqueries start fresh. `createEvents`, `readFile`, `readPersistedAggregation` and `correlate` count as aggregates for this rule.
- Function-valued arguments require calls: `stats(count)` reports `CQL_ARGUMENT_TYPE`; write `stats(count())`. 0.1.7 accepted bare aggregate names, including in lists and `groupBy` function arguments.
- Direct assignment requires a function with an `as` parameter: `v := collect(user)` reports `CQL_ASSIGN_ALIAS`. An explicit `as` next to assignment is also rejected. 0.1.7 accepted assignment to functions without `as`.
- Aggregates and joins in conditional branches report `CQL_BRANCH_FUNCTION`, as in `case { count(); * }`. 0.1.7 accepted them; place aggregation or joins outside `case` and `match` branches.
- Argument binding is stricter: `parseTimestamp(timestamp)` reports `CQL_ARGUMENT_REQUIRED` because its unnamed argument is `format` and `field` must be named; `math:mod(y, 3)` and `setTimeInterval(1d)` report `CQL_ARGUMENT_COUNT`. Use `parseTimestamp("millis", field=timestamp)`, `math:mod(y, divisor=3)` and `setTimeInterval(start=1d) | count()`. 0.1.7 used different unnamed-argument rules.
- Reserved free-text words and mixed-case operators report `CQL_RESERVED_WORD`, as in `a=1 Or b=2`; 0.1.7 accepted them. Invalid quotation delimiters report `CQL_QUOTE`, as in `a=“1”`; 0.1.7 accepted curly delimiters or reported unsupported syntax for single quotes/backticks. Unquoted `$` reports `CQL_SYNTAX`, as in `a=$x`; quote literal text.
- Row limits are 1..200,000 and group limits 1..1,000,000, or `max`; out-of-range numbers report `CQL_ARGUMENT_RANGE`. `head(0)` and `table([a], type=any)` are rejected; 0.1.7 accepted them. `top(a, limit=24577)` reports `CQL_ARGUMENT_RANGE`; its ceiling is 24,576 rather than the larger ceiling accepted in 0.1.7.
- Calls combined with Boolean operators report `CQL_FUNCTION_FILTER_COMPOSITION`, as in `lower(y) OR z=2`; 0.1.7 returned an unknown result. Use pipes for conjunctions or `case` for alternatives.
- Literal arguments convert to required types: `head("2")`, `count(a, distinct="true")`, `in(a, values=1)` and `in(a, values=[3, 6])` are accepted. 0.1.7 rejected these forms or reported `CQL_UNSUPPORTED_STRING_ARRAY_SINGLETON`. Parameter choices still apply; sort order accepts ascending/descending and case variants.
- Regex literals accept repeated `g/m/i/d/F` flags; other flags report `CQL_REGEX_FLAGS`. `a=/x/gi` was unsupported in 0.1.7. Function flags keep separate rules. Parameter defaults supply values, as in `a=?{p="1"}`; 0.1.7 reported unsupported syntax. Parameters without defaults remain unsupported.
- One leading or trailing empty stage is accepted with `CQL_EMPTY_STAGE`, as in `x=1 |`; 0.1.7 rejected it. Interior empty stages remain errors. Unknown string escapes retain their backslash, as in `p="a\qb"`; 0.1.7 reported `CQL_STRING_ESCAPE`.
- `text:editDistanceAsArray` requires an array suffix, as in `text:editDistanceAsArray(target=b, references=["a","b"], maxDistance=2, asArray="d[]")`; 0.1.7 accepted the unsuffixed prefix and reported `CQL_UNSUPPORTED_ARRAY_NAME` for the suffixed form.
- Accepted text filters gain warnings: `x=1 | count` reports `CQL_BARE_FUNCTION_NAME`, `where a=1` reports `CQL_BARE_COMMAND_WORD`, `a=1 && b=2` reports `CQL_OPERATOR_TEXT`, and `a=null` reports `CQL_NULL_TEXT`. 0.1.7 gave none of these warnings. Use parentheses for calls, CQL filters/operators, and presence tests for missing fields, or quote intended text.
- Mixed `or` and `and` gains informational `CQL_OR_PRECEDENCE`, as in `a=1 or b=2 and c=3`; `or` binds tighter. Control escapes followed by letters/digits warn with `CQL_STRING_ESCAPE_CONTROL`, as in `p="C:\temp"`. 0.1.7 gave neither diagnostic.
- Negated transforms are accepted with `CQL_NEGATION_NO_EFFECT`, as in `!lower(a)`; 0.1.7 rejected them. Aggregate/source/definition calls and `eval` remain invalid under negation. `tail` after a known removal of `@timestamp` warns with `CQL_TAIL_WITHOUT_TIMESTAMP`, as in `count() | tail(1)`; 0.1.7 gave no such warning.
- Hosted error answers such as `{"result":{"error":"Search failed"}}` report `MCP_TOOL_ERROR`; recognized hosted cutoffs report `MCP_DEADLINE`, regardless of the envelope error flag. 0.1.7 reported `MCP_SHAPE`. Resumable discovery now ends attempts on recognized final answers, including unusable completed results: the attempt remains charged, the run pauses, and explicit resume retries as a new attempt. Lost responses still require settlement; 0.1.7 left these attempts blocked.
- Saved-result assessment reports `RESULT_TIMEOUT` or `RESULT_ERROR` for hosted error answers instead of the unsupported-shape verdict in 0.1.7. Empty and zero-count answers, such as `{"result":[{"_count":0}]}`, ask for a positive control: rerun without the selective filter or field and confirm a non-zero count before concluding no matches. 0.1.7 did not ask for that control.
- The profile remains `cqlmatic-ngsiem-core-v3` with a new knowledge revision. Core-v3 packs from 0.1.7 remain readable with their original bindings. Checkpoint inspection admits 0.1.7 alongside earlier supported producers; lifecycle actions still require the producing release. For example, selecting a 0.1.7 run for resume in 0.1.8 reports `MCP_STATE_PRODUCER`. Request, status, pack and inventory versions are unchanged from 0.1.7.

## 0.1.7

- The executable profile is `cqlmatic-ngsiem-core-v3` with a new knowledge revision. Raw checking and typed function calls cover 194 Query candidate function names with bounded contracts, up from 67: 193 current candidates and deprecated `lowercase`, which remains distinct from `lower`. The bundled function ledger lists parser-only `copyEvent` and unreleased `math:spherical2cartesian` as excluded.
- `catalog --limit` accepts 1–250 for ordinary, function and standard lookup. `catalog --functions` entries add `requirements`, `parameters` and `scope`, and the `readFile` entry adds `variadic_argument`.
- `catalog --profile` adds `function_scope_counts`, `form_assessments` and `scope_reviewed_at`. Its `knowledge_revision` is now a 64-character SHA-256 over the bundled reference files.
- Functions and forms with a documented minimum version, feature or resource prerequisite add a `CQL_TARGET_REQUIREMENT` warning. This includes calls that were warning-free in 0.1.6, such as `wildcard`, `if`, `coalesce`, `getField`, `match`, `readFile`, `defineTable`, `correlate`, `asn`, `ipLocation` and `ioc:lookup`. The outcome stays `ready`, but `--fail-on-warning` returns exit 1 for these queries.
- `CQL_FUNCTION_LIFECYCLE` warns about documented experimental, beta or deprecated functions and forms. Capability evidence does not remove it.
- Argument choices and numeric bounds follow bundled documented parameter facts. Among functions supported in 0.1.6, `sort(limit=max)`, `sort(type=hex)`, `table(type=hex)`, `table(type=any)` and `head(0)` are accepted, and `drop` and `selectLast` accept a single unbracketed field. Numeric bounds are checked against both the literal's exact decimal value and its double-precision reading, and numbers that overflow are rejected.
- Some 0.1.6 forms change: `default` takes `value` as its positional argument, so write `default(field=user, value="x")`; the `rest` argument of `top` accepts only `true` or `false`, quoted or unquoted; `parseJson` `handleNull` must be `discard`, `empty` or `keep`; and `array:contains` treats `value` as a string, so `value=a` no longer reads a field `a` and `value=a+1` is unsupported. `neighbor` is classified as an aggregate.
- `setTimeInterval` must appear once, first in the top-level query (`CQL_TIME_INTERVAL_PLACEMENT`), and always reports `CQL_QUERY_TIME_OVERRIDE` because it overrides the API or UI time range. `eventSize`, `eventFieldCount` and `eventInternals` must precede aggregation and source replacement (`CQL_STORED_EVENT_PLACEMENT`), and `reverseDns` must follow an aggregate in the top-level pipeline (`CQL_REVERSE_DNS_PLACEMENT`).
- Time interval endpoints on `setTimeInterval`, `join`, `defineTable`, `remoteTable` and `readPersistedAggregation` support bounded fixed relative durations, signed offsets, epoch values and offset-qualified timestamps, and the `slidingTimeWindow` span supports fixed durations. Other spellings, including zero durations, are unsupported. All five functions reject explicit endpoints that are provably reversed; `setTimeInterval` also checks its default end of `now`.
- `accumulate`, `partition`, `slidingWindow` and `slidingTimeWindow` require a preceding aggregate (`CQL_SEQUENCE_PLACEMENT`) and warn when its row order is not established (`CQL_SEQUENCE_ORDER`). Sub-aggregations of `accumulate`, `slidingWindow` and `slidingTimeWindow` must output at most one event (`CQL_SEQUENCE_AGGREGATE_ROWS`), and `stats` cannot pair a sequence function with a multi-event sibling (`CQL_SEQUENCE_STATS`). `window` is accepted only as the aggregate of `bucket` or `timeChart` (`CQL_WINDOW_PLACEMENT`), with exactly one of `span` or `buckets` (`CQL_WINDOW_WIDTH`).
- `percentile` reports `CQL_APPROXIMATE_PERCENTILE`, a `math:mod` divisor or `math:pow` exponent that is not an integer literal reports `CQL_MATH_PARAMETER_CONTRACT`, and `lowercase` with `include=fields` or `include=both` reports `CQL_LOWERCASE_RETENTION`. Computed `setField` targets and wildcard `lowercase` fields report `CQL_UNSUPPORTED_DYNAMIC_OUTPUT`; `array:reduceRow` without a single-event, single-field aggregate reports `CQL_UNSUPPORTED_REDUCER_OUTPUT`.
- Direct assignment accepts `splitString` without `index`, `rename`, `parseUrl` and `eventSize`, writing their output to the assigned name, and single-output aggregates such as `n := count()`. Assigned aggregates obey the same placement restrictions as their call forms, and assigned calls and `match` subjects report `CQL_DROPPED_FIELD` when they read a field that an earlier projection removed. Combining `:=` with an explicit `as` argument reports `CQL_ASSIGN_ALIAS`.
- Aggregate `function` arguments accept composite pipelines that aggregate, such as `stats({head(1) | count()})`, and bare aggregate names without required arguments, such as `count`. A composite pipeline that does not aggregate reports `CQL_AGGREGATE_REQUIRED`.
- Raw checking accepts `field =~ !function(...)` negation, bare glob patterns in `wildcard` such as `wildcard(*foo*)`, and the regex `F` flag. The `g` flag remains unsupported.
- Saved-query and resource invocations such as `$name()` report `CQL_UNSUPPORTED_SYNTAX`. `$` text in patterns, strings, regex literals and comments is unaffected.
- Unresolved `?parameter` values in typed, nested and aggregate arguments report `CQL_UNSUPPORTED_PARAMETER` with outcome `unsupported`, without additional type or value errors for the parameter. Independent errors are still reported.
- A single string where a string array is expected, such as `in(field=user, values="alice")`, reports unsupported `CQL_UNSUPPORTED_STRING_ARRAY_SINGLETON` instead of an invalid argument type.
- After `createEvents`, only `@rawstring`, `@timestamp`, `@timestamp.nanos` and fields the query writes count as query-produced; strict grounding needs context for other field names.
- After a field pack is active, inventory offers optional function capability checks through the terminal entry **capabilities (optional)** and the actions `prepare-capabilities`, `dispatch-capability`, `submit-capability`, `pause-capabilities` and `resume-capabilities`. They are off by default; empty input or **later** prepares nothing and leaves the field map unchanged. The fixed cases are `array-union`, `array-intersection`, `array-reduce-row`, `array-reduce-column` and `math-sqrt`, with a separate allowance of 1–1,000 attempts and 1–14,400 active seconds. Preparation requires protected search-lifetime evidence; preparation and reservation do not run a search.
- `generate` and `check` add `--execution-context-id`, and generate, check and assess request contexts accept `execution_context_id`; the flag overrides the request value. A current observation from an array case that matches the environment, CID and view, authorization context, case revision and argument shape turns that form's `CQL_TARGET_REQUIREMENT` into informational `CQL_TARGET_OBSERVED`. Positive observations expire 30 days after result retrieval and a newer unknown attempt supersedes them; the CID alone never qualifies.
- Full and summary status add `capabilities` and `capability_blocked`; brief status adds `capability_blocked` and `capability_run_count`. An unsettled capability search blocks further inventory searches and sets the brief blocker `capability-termination-unresolved` with `CAPABILITY_SETTLEMENT_REQUIRED`. Status suggests the optional checks once a field pack is active.
- `discovery-step`, `dispatch-discovery`, `pause-discovery` and `resume-discovery` accept an optional zero-based `run_index` into `discovery_runs`; omitting it selects the latest run. Replies include the resolved index, and brief failures keep only its `/discovery_runs/N` pointer.
- Inventory-created discovery checkpoints record their owning inventory. Standalone `env discover --mcp --dispatch` and `--resume` reject them with `DISCOVERY_INVENTORY_OWNER`; pause, answers and settlement still work. Retained resumable checkpoints written by the running version gain this association when inventory next prepares discovery, refresh, scout or capability work, dispatches discovery, refresh or capability searches, or resumes discovery or capabilities, even if that action is then refused for a reason unrelated to earlier-release history.
- Discovery checkpoints written by earlier releases remain inspectable after an upgrade: format 2 from 0.1.0–0.1.6 and format 3 from 0.1.6. A different supported version is not reported as tampering. Dispatch, resume, step, pause, settlement, activation and cleanup stay bound to the version that wrote the checkpoint; selecting such a run returns `MCP_STATE_PRODUCER` and leaves the inventory and every retained checkpoint unchanged. Completed and terminally failed runs from 0.1.6 do not block new work and keep their original pack identity.
- An unfinished resumable run from an earlier release that has no owner binding blocks guarded inventory work with `MCP_STATE_PRODUCER`, even when safely paused, because its producing version could still resume it independently. Finish it with the producing release before upgrading. Afterwards it can still be finished with that release's standalone `env discover --mcp --state CHECKPOINT` resume, dispatch and answer steps, including when the inventory has already been migrated or the run is no longer the latest; a run finished that way stays readable history and is not integrated into the inventory automatically.
- A hosted cancellation counts as terminated only when its saved evidence matches the exact attempt; otherwise the checkpoint is rejected as `MCP_STATE_TAMPERED`. Native cancellations or failures without confirmed cleanup stay uncertain and keep blocking further inventory searches.
- Discovery checkpoints reject more than one successful attempt for the same probe, so one accepted result cannot stand in for several dispatches.
- Native cleanup attempts every uncertain job it can identify, even after an earlier cleanup or checkpoint save fails, and keeps unresolved uncertainty and existing budgets unchanged.
- Blockers that do not come from a discovery run, such as an unresolved refresh or capability search, carry no `/discovery_runs/N` pointer. Inventory and checkpoint paths that are not valid UTF-8 return `LOCAL_PATH` or `INVENTORY_INPUT` instead of ending the process abnormally.
- A discovery run that completes after the cumulative inventory changed is recorded as `superseded` instead of failing. Its pack and receipt are retained, the active inventory is unchanged and the run grants no pending-work credit; the action exits 0 with `status: "incomplete"` and `DISCOVERY_SUPERSEDED`.
- `sort`, `head`, `tail`, `table` and `groupBy` with `limit=max` are assessed against the target's unknown `StateRowLimit` or `GroupMaxLimit` instead of a fixed number: assessment reports inconclusive `RESULT_UPSTREAM_CAP_UNVERIFIED` in any position and omits that limit from `caps`. A negative, parameterized or unparseable limit is likewise unverified instead of being reported as a default. A saved result that was `no-findings` in 0.1.6 can become `inconclusive`.
- Aggregates with a documented default limit in the bundled parameter data, such as `selfJoin`, `series`, `fieldstats` and `transpose`, are inconclusive whether the limit is written or omitted.
- A final stage that returns more rows than its own limit allows is inconclusive with `RESULT_CAP_EXCEEDED`, including an earlier row limit, written directly or assigned, followed only by call-free filters (including `OR`), `select`, `drop`, `rename`, `head`, `tail`, `sort` or call-free assignments. After any other later stage, rows above an explicit earlier limit are inconclusive unverified uncertainty. A stage that replaces the source ends the earlier limit.
- A final `groupBy` whose sub-aggregation can return several rows per group counts distinct grouping-key tuples only when every key is a plain field name and every sub-aggregation is on a fixed list of key-preserving calls, or an inline pipeline of comparison filters and those calls. A key absent from a row counts as its own value, unless the row holds another spelling of the same data. Array, indexed or wildcard keys, such alternative spellings, and outputs that can refer to the same data as a key leave the group count unverified.
- A collected value list stays countable only through outputs that copy it exactly: listed keys and value selectors, and under grouping or `stats`, listed selector sub-aggregates. Field names are compared by overlap, so a computed output, alias or assignment that can refer to the same data invalidates the list. These stages also mark it uncountable when they remove or rename the field away, even if the name is recreated later: projection, `drop`, `array:drop`, `array:rename`, `lowercase` renaming, a non-exact rename, and an unassigned aggregate that does not output it. Lineage through an aggregate assigned to a new name is not covered. After branches the list survives only if every branch keeps it. `multival=false` written as a boolean is recognized.
- Column statistics take one pass over the returned rows, so results whose rows carry distinct keys are assessed in linear time. `columns` and `RESULT_NULL_FIELDS` list at most 1,000 columns; `RESULT_COLUMN_REPORT_LIMIT` reports the totals, and the outcome still covers every column.
- Saved-result assessment follows `array:drop` and `array:rename` of a literal array such as `a[]` like `drop` and `rename`: the elements the query writes from `a[0]` up to the first gap are no longer expected, or are expected under the new array name with any count meaning, so a correct result no longer gets a false `RESULT_NULL_FIELDS` for `a[0]`. A result that still holds the old element names after `array:rename` is now reported as missing the new ones. Elements after a gap, structured members, array arguments without `[]` and a destination's other existing elements stay expected.
- Assessment reports inconclusive `RESULT_QUERY_COVERAGE` for a stage outside the modeled function catalog, with unresolved or unsupported arguments or parameters, or without a complete output model. Informational `RESULT_OUTPUT_COVERAGE` notes functions that write dynamically named fields while other checks continue.
- Inventory state version 4 adds optional `capability_runs` and producer-managed `field_evidence_schema_version`. Versions 1–3 remain readable. Any state-writing action, including generation or checking that queues inventory hints, migrates the state to version 4; migration keeps field evidence and does not by itself invalidate an existing reconciliation. Status reads do not migrate state.
- On Windows, files and lock files opened for protected writes are rejected with `LOCAL_FILE_TYPE` when they are reparse points, as symbolic links already were.
- On Windows, checking an existing protected input verifies its parent directory and the file in one helper process instead of two. The ACL checks and their order are the same, and a failure reports the same diagnostic when the paths and their protection do not change during the check. Both phases now share the helper's single 20-second limit.
- Request, status and pack format versions remain 1. New and refreshed packs record `cqlmatic-ngsiem-core-v3` and the new knowledge revision. Accepted legacy core-v1 and core-v2 packs must keep their original knowledge revision and retain their profile and digest.
- A 0.1.6 binary cannot read inventory state written by this build (version 4). Preserve the earlier state file before upgrading if you may return to 0.1.6.
- A 0.1.6 binary rejects core-v3 packs with `PACK_PROFILE` and cannot open discovery checkpoints that carry inventory owner metadata, even as completed history.
- A 0.1.6 binary rejects requests that include `execution_context_id`, `run_index` or a capability action, and does not accept `--execution-context-id`.

## 0.1.6

- Manual refresh prepares a shallow source census for the confirmed view, with a finite provider search lifetime and protected dispatch, settlement and import steps. A 30-day reminder offers refresh or deferral; startup does not run searches automatically.
- Both Full and Quick query writing can queue bounded unverified source and input-field hints. Pending work remains visible in Settings until applicable inventory or an explicit exclusion resolves it.
- Eligible partially completed Codex CIMD setup can recover through inspection, a fresh confirmation preview and native login without replacing or duplicating the existing entry. Authentication and tool discovery still need a matching host report.
- New discovery checkpoints support pause, cancellation settlement and resume while retaining accepted captures and remaining attempt/active-time budgets. Uncertain searches block further inventory searches until safely settled; hosted cancellation remains the host's responsibility.
- Valid late MCP responses can settle their exact attempt without becoming discovery evidence. Complete native captures can finish local activation after the search budget expires. Pending hints resolve only from applicable subsequent measurements, including separate completed batches; terminal EOF does not defer notices.
- Large valid discovery packs can save inventory completion without being counted twice against pending-work analysis. Reaching that analysis budget preserves completed discovery and leaves unproven notices pending.
- Sparse sources with positive whole-window volume and an empty recent fieldset receive one source-bound whole-window fallback within the original budgets. Fieldset names remain schema hints unless qualifying measurements supply population evidence.
- `status` and inventory actions add `--json --brief`, a projection capped at 4,096 UTF-8 bytes. It reports readiness, counts, reminders and opaque pending-work references without returning the full map.
- Query parsing and rendering preserve quoted Boolean-keyword field names, including dotted and indexed names. The supported `concat` signature uses a field list without a separator parameter.

## 0.1.5

- Inventory rejects pack rollback and discovery activation from a stale inventory predecessor. Discovery artifacts remain bound to their prepared run, destination and pack bytes; failed activation preserves earlier evidence.
- Replaying an unchanged import preserves current-version inventory bytes, timestamps and reconciliation. Exact saved-query replay validates the protected originals and retained audit, and can restore a missing audit safely.
- Saved-query imports reject a changed retrieval time for the same capture. `uncredited_fields` and `next_action` identify direct query input fields without positive returned values. Strict grounding still evaluates the inventory, packs and source requirements.
- Scout preparation and import validate the bound environment, discovery mode and capture ordering. Replaying the same accepted scout preserves state; changing the target or mode requires a new matching preparation.
- Parser imports validate retrieval timestamps before saving captures. Automatic inventory target diagnostics identify the actual Full or Quick mode.

## 0.1.4

- Generation, checking and saved-result assessment automatically reuse a matching confirmed Full or Quick inventory's active pack and otherwise unspecified target. Explicit packs remain primary; matching inventory guards still apply to generation/checking. Assessment adds `--inventory-state` without deriving population rates from the query ledger or saving leads.

### Compatibility

- Package version, capability profile, and JSON schema version are independent. This release uses `cqlmatic-ngsiem-core-v2` and request schema version 1.
- Packs include `record_kinds`; use the bundled schema when consuming them. Supported legacy core-v1 packs retain their original evidence and digest.
- MCP state format 2 binds the discovery algorithm, destinations, and frozen activation bytes. Older state files require a new run. Interrupted activation resumes without merging evidence twice.
- Text files use LF line endings. Keep them as LF when running schema drift checks on Windows.
